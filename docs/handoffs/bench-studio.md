Bench Studio's situation is unlike the other subscribers', so this handoff reads differently too. **1.2 changes nothing about the exception you were granted, and asks no new permission either.** It changes what the ground under a pinned run is made of: which names exist at all, which of them can be reached without anyone choosing them, and what answers a request that names nothing. A benchmark's whole claim is that its number belongs to one named model, so the three things 1.2 unsettles are exactly the three you care about most.

## The 1.2 delta, in the order a client reads it

1. **§3: `daytime` is no longer promised in every configuration.** The old row said "Present in **every** configuration." It now reads: "Present in every **normal** configuration: every configuration that runs a Daytime resident. The AI Runtime may publish a configuration in which no catalog entry declares `daytime`, and then there is none to send. That is not a licence for a client to invent one, or to send something else instead of it." Nothing declares such a service in `offline_services`, because nothing stopped it: the answer is 404 `MODEL_NOT_FOUND`, not 503 `SERVICE_OFFLINE`.
2. **§3: a new service ID, `trial`** — "Present **only** while a trial configuration is selected, and only under that name: it is opt-in, it is never the configuration the operator falls into, it is never an alias of `daytime` or of any other service, and in every other configuration it is **404 `MODEL_NOT_FOUND`**." §3 adds "**An opt-in service is never a fallback, in either direction**… When `trial` does not answer, the client reports that; continuing on a model nobody selected is not recovery", and §10's `MODEL_NOT_FOUND` row ends "Never fall back from an opt-in service such as `trial`". A benchmark has no fallback to give up, so this rule arrives already met — what it means for a measurement is the mirror image of the fallback case: no service the operator did not choose may end up being the model a result belongs to.
3. **§3: new subsection "Two kinds of names."** **Catalog service IDs** — `daytime`, `nighttime`, `trial`, and every other alias the published catalog declares — exist only while some entry declares them: absent is 404, deliberately stopped is 503, and `ids` lists every name accepted right now. The **compatibility alias** `local-active` is reserved and **not a service**: accepted with no entry declaring it only in the router's **legacy single-marker mode**; in catalog mode — what this deployment runs — it is an ordinary declared alias that only the configuration's default entry may declare. Either way it resolves to "the model this router has active right now": an alias of the active slot, not of `daytime`, following every switch the operator makes, and its stability column now reads "Kept for compatibility. **Do not adopt it.**"
4. **§3: a request that omits `model` is answered by the active configuration's default, which is not promised to be `daytime`.** Where 1.1 read "An omitted model selects `daytime`", 1.2 reads: "An omitted model selects the default of the **active configuration**, which this contract does not promise is `daytime`: while a trial configuration is selected, an omitted model is answered by the trial. A client that must not be served by a particular model MUST send an ID." State this case as explicitly as the named-ID cases: it is the **only** route by which an opt-in trial ever answers a request that never named it — no fallback, no substitution, no error. For a benchmark the stakes are sharper than anyone else's: an unnamed request does not merely risk the wrong model, it makes the measured model unknowable, and a result whose model is unknowable cannot be compared with anything.
5. **§3 + §4: a catalog entry with no service alias is not addressable and MUST NOT be surfaced.** Such an entry has no name a conformant client may send; the router lists it with `service` set to its canonical ID because it will not invent one, and §3 says the model is "not selectable under this contract and MUST NOT be surfaced as a model a person can choose". §4 gives the reading rule: **`service === id` is how a model with no addressable ID reads.** [MODEL_DISCOVERY.md — a catalog entry with no service alias](https://github.com/astigmatism/llm-router/blob/0b1668669214a7c67cbba8008ddc98ffc1e14b72/docs/MODEL_DISCOVERY.md#a-catalog-entry-with-no-service-alias) explains why `service` reports the canonical ID rather than a fabricated name. Bench Studio is the one subscriber permitted to *hold* a canonical ID — for one run — which is why this item belongs in its own words: §3 grants pinning a canonical ID **derived from a service ID at launch**, and says nothing that makes a canonical ID into a service ID.
6. **[STABLE_SERVICES.md](https://github.com/astigmatism/llm-router/blob/0b1668669214a7c67cbba8008ddc98ffc1e14b72/docs/STABLE_SERVICES.md) now lists `trial`, and the `daytime` context figure is corrected to 163840** (it said 131072). Informational: your budget comes from the live document, and §8 still forbids hard-coding a context size. The `trial` row records that it declares no image input.
7. **Two additive diagnostics a client MAY ignore.** `CATALOG_HAS_NO_SERVICE_ID` in the capabilities document's `warnings` (with `complete: false`) says no entry of the active catalog declares a service ID; `MODEL_HAS_NO_SERVICE_ID` in one model's discovery `x_ollama_router.warnings` (with that entry incomplete) says that entry declares none. Both are the router's own finding; §11 lets fields be added without a version change and clients MUST ignore what they don't know, so neither is ever a reason to invalidate, block or fail a run. The runtime's `deployment_warnings` are a separate fact and **still pass through verbatim as `metadata.qualification_notes`** — the publisher's note, not the router's, and the two never merge.

## Why 1.2 is still a minor version

§11: *"A minor version (1.1, 1.2, …) only clarifies or adds permissions and never requires client changes, so copies of an earlier minor version stay valid until the next update handoff."*

- Your §3 exception is untouched, word for word: resolve at launch, pin the canonical for the run, never keep canonical IDs as configuration, `404` = the model changed and `503` = offline, neither ever a reason to switch.
- 1.0 §3 already required service IDs (`daytime`, `nighttime`), already forbade configuring or persisting canonical IDs outside a pinned run, and already made an unknown ID `404`. 1.2 widens the sendable set to "another service ID the current document advertises" and removes opt-in names from every candidate pool: a permission plus a carve-out, neither of which binds a client with no fallback and no hard-coded targets.
- The corrected `daytime` guarantee removes a promise the router could not keep; `resolve` already required the name to be present in the live document, which is exactly what may now fail, and your absent/offline split anticipated it.
- `service === id` and the omitted-`model` correction restate rules 1.0 already stated ("MUST NOT configure… canonical IDs"; "A client SHOULD always send a model"). Bench Studio meets both today, and this handoff asks for the map to say where.
- The two warnings are additive fields §11 already says clients MUST ignore, and Bench Studio already ignores them.

If re-verifying an item turns up a change you must actually make, report it as a contract defect: that would make 1.2 a 2.0, and the other four subscribers would have to be told again before they replace anything.
