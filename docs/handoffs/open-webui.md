## The 1.2 delta, in the order a client reads it

1. **§3: `daytime` is no longer promised in every configuration.** The table used to say "Present in **every** configuration." It now says present in every **normal** configuration — every configuration that runs a Daytime resident — and adds: "The AI Runtime may publish a configuration in which no catalog entry declares `daytime`, and then there is none to send. That is not a licence for a client to invent one, or to send something else instead of it." Such a configuration does not list `daytime` in `offline_services` — it never stopped it — so the answer is 404 `MODEL_NOT_FOUND`, not the 503 `SERVICE_OFFLINE` your enforcer was designed around.
2. **§3: a new service ID, `trial`.** Present **only** while a trial configuration is selected, and only under that name: opt-in, never the configuration the operator falls into, never an alias of `daytime` or of any other service, and **404 `MODEL_NOT_FOUND`** everywhere else. §3 ("An opt-in service is never a fallback, in either direction") and §5 ("Opt-in services are never candidates") make it a name a client may use only when its own operator chose the matching configuration. Open WebUI serves three people from one shared picker, so for this project that rule is about **who is shown what**, not about retry policy.
3. **§3: new subsection "Two kinds of names".** **Catalog service IDs** (`daytime`, `nighttime`, `trial`, and every other alias the published catalog declares) are contract-governed and exist only while an entry declares them — absent is 404, deliberately stopped is 503 — and `ids` in the capabilities document lists the names accepted right now. `local-active` is the other kind: a reserved compatibility alias, **not a service**, accepted with no entry declaring it only in the router's **legacy single-marker mode**, and in catalog mode — what this deployment runs — an ordinary declared alias that only the configuration's default entry may declare. Either way it names **the model this router has active right now**, not Daytime, and it follows every switch the operator makes. Its stability column now reads "Kept for compatibility. Do not adopt it."
4. **§3: a request that omits `model` is answered by the active configuration's default, which is not promised to be `daytime`.** The old line read "An omitted model selects `daytime`." It now reads: "An omitted model selects the default of the **active configuration**, which this contract does not promise is `daytime`: while a trial configuration is selected, an omitted model is answered by the trial. A client that must not be served by a particular model MUST send an ID." Say this case as explicitly as the named-ID cases, because it is the **only** route by which an opt-in trial ever answers a request that never named it — not a fallback, not a substitution, not an error path. Only silence about the model can do it, so for Open WebUI the guarantee belongs in the preset's `base_model_id` and in every request the overlay builds.
5. **§3 + §4: a catalog entry with no service alias is not addressable and MUST NOT be surfaced.** The router lists such an entry with `service` set to its canonical ID, because it will not invent a name, and §3 says the model is "not selectable under this contract and MUST NOT be surfaced as a model a person can choose". §4 gives the reading rule: `service === id` is how a model with **no addressable ID** reads. [MODEL_DISCOVERY.md — a catalog entry with no service alias](https://github.com/astigmatism/llm-router/blob/0b1668669214a7c67cbba8008ddc98ffc1e14b72/docs/MODEL_DISCOVERY.md#a-catalog-entry-with-no-service-alias) explains why the field reports the canonical ID: a row that `/v1/models` or `/api/tags` can resolve is not a row a contract client may send. For an enforcer that writes a shared picker, this is the rule that decides what never becomes a row.
6. **[STABLE_SERVICES.md](https://github.com/astigmatism/llm-router/blob/0b1668669214a7c67cbba8008ddc98ffc1e14b72/docs/STABLE_SERVICES.md) now lists `trial`, and the `daytime` context figure is corrected to 163840.** It said 131072. Both are what today's catalog declares, not a promise; §8 still forbids hard-coding a context size, which is why preset labels follow the live document rather than that table.
7. **Two additive diagnostics a client MAY ignore.** `CATALOG_HAS_NO_SERVICE_ID` in the capabilities document's `warnings` (with `complete: false`) says no entry of the active catalog declares a service ID; `MODEL_HAS_NO_SERVICE_ID` in one model's discovery `x_ollama_router.warnings` (with that entry incomplete) says that entry declares none. Both are the router's own finding, both are optional reading — §11 permits fields to be added without a version change and clients MUST ignore what they don't know — and neither changes inference or a status code. The runtime's `deployment_warnings` remain a separate fact and **still pass through verbatim as `metadata.qualification_notes`**; the new codes never replace or merge into those notes, which matter to this project because an unqualified-experiment note is how the runtime marks a model people should not be handed casually.

## Why 1.2 is still a minor version

§11: *"A minor version (1.1, 1.2, …) only clarifies or adds permissions and never requires client changes, so copies of an earlier minor version stay valid until the next update handoff."*

- The enforcer's row creation is driven by the two service aliases it knows, so `trial` is simply a name it never adopts — no change, and no permission it has to take up.
- The corrected `daytime` guarantee removes a promise the router could not keep; a client that reads the document each cycle and shows the reason, as the enforcer does, is unaffected.
- The no-alias rule and the omitted-`model` correction restate what 1.0 §3 already required of a conformant client: send a service ID, never a canonical ID, never a name the router did not offer.
- The two warnings are additive fields §11 already says clients MUST ignore.

If any item above turns out to need a code change, report it as a contract defect: that would make 1.2 a 2.0, and the other four subscribers would have to be told again before they replace anything.
